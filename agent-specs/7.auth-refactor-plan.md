## 2. Target architecture (one boring path)

### Principle

Token-in-email flows use **one submission model** aligned with login/set-password:

```
Browser form  →  POST (JSON or server action)  →  acceptAdminInvite()  →  redirect success
```

No credentials in URL. Token travels in POST body (hidden field or JSON). Client JS improves UX but is not required for correctness.

### Recommended direction: **Option A — RHF + POST API (consistent)**

| Layer | Choice |
| --- | --- |
| Form | `<form method="post" noValidate onSubmit={bindFormSubmit(...)}>` **or** explicit `preventDefault` + fetch |
| Submit | `adminJson` POST `/api/admin/accept-invite` (same as login) |
| Token | SSR `inviteToken` prop → hidden input **or** closure in submit handler; drop sessionStorage unless proven needed |
| Success | Redirect to `/accept-invite?done=1` or inline success state |
| Remove | `accept-invite-action.ts`, duplicate GET recovery probe if SSR always has token |

**Option B — server action only:** Keep action, delete POST route, add `method="post"` + `preventDefault` guard. Document exception to “React Query → `/api/admin/*`” in design spec.

**Pick one in Phase 1; do not maintain both.**

### Token persistence (after refactor)

| Mechanism | Keep? |
| --- | --- |
| SSR `?token=` on invite link | Yes — source of truth |
| Server redirect stripping leaked query keys | Yes — safety net |
| `InviteTokenScript` + sessionStorage | Remove after E2E green unless cross-tab recovery still needed |
| Client GET `/api/admin/accept-invite?token=` for email | Optional — prefer SSR `inviteTokenEmail()` on page |

## 3. Phased plan

### Phase 0 — Stabilize (P0, one story)

**Goal:** Invite accept works on cross-machine dev path without credential leak.

1. Add E2E: seed invite token → open `/accept-invite?token=…` → fill profile → submit → assert `?done=1` or success callout → login with new username.
2. Assert URL never contains `password=` after submit.
3. Harden form: `method="post"`, `onSubmit` with `preventDefault`, hidden `token` from SSR.
4. Align submission with login (Option A) **or** harden server action (Option B).
5. Migrate `useFormState` → `useActionState` if server action kept.
6. User confirms usable on their path (second machine + email link).

**DoD:** E2E green in CI; manual confirmation; no layered workaround without a test explaining why.

### Phase 1 — Consolidate (P1)

1. Remove dead code (unused POST route **or** server action — whichever loses).
2. Merge expired UI into one component (`AcceptInviteExpiredScreen` only).
3. Call `clearInviteToken()` on success/expired; remove sessionStorage if unused.
4. Expand unit tests: expired token, username taken, mismatch, invalid username, `token-validation` routing.
5. Integration test: page redirect when `?password=` present.

### Phase 2 — Dev ergonomics (P1)

1. Document cross-machine dev in [`6.agent-deployment.md`](./6.agent-deployment.md) § Local dev:
   - `PUBLIC_BASE_URL=http://<host-ip>:<PORT>` so invite mail links open on the testing machine.
   - `ALLOWED_DEV_ORIGINS=<host-ip>` for Next.js dev (comma-separated).
2. Remove hardcoded `10.0.0.142` default from `next.config.ts`; require env or document in deployment spec.
3. Propose `.env.example` keys (operator confirms per `protect-eng`).

### Phase 3 — Spec and UX alignment (P2)

1. Sync AC, UI design, route table (this doc batch).
2. Add mock-up `14-accept-invite.html` or update index to reference implemented screen keys.
3. Consider post-invite auto-login (product decision — not required for MVP if manual sign-in is accepted).
4. Password strength rules (product decision — document if deferred).

## 6. Anti-patterns (do not repeat)

- Ship token-in-URL forms without E2E submit proof.
- Stack client mitigations (sessionStorage, URL scrub, div-not-form) without fixing native submit.
- Bundle invite onboarding with unrelated UI fixes in one delivery.
- Verify API with `curl` only and call the story done.
- Declare done without user confirmation on their real test path (cross-machine email).

## 7. Decision log

| Decision | Choice | Rationale |
| --- | --- | --- |
| Submission path | **Option A — RHF + POST `/api/admin/accept-invite`** | Matches design spec §12 and login/set-password |
| Post-invite login | Manual sign-in (`?done=1`) | Current behavior; auto-login is optional Phase 3 |
| Invite URL path | `/accept-invite?token=` | Implemented; replaces set-password for invites |
| Cross-machine dev | Supported via `PUBLIC_BASE_URL` + `ALLOWED_DEV_ORIGINS` | Valid operator workflow when local mail fails |
| Post-invite sign-in | **`GET /login/fresh`** route handler clears session cookie | Next.js forbids `cookies().delete()` in Server Components; replaced `/login?fresh=1` page logic |
